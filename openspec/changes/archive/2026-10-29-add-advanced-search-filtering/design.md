## Context

The search workspace owns the entire results subtree. Advanced controls therefore share one typed state model rather than communicating through htmx swaps or ad hoc DOM events. The system must remain useful if future filters include computed quality/relevance scores or posterior probabilities generated by server-side models.

## Goals / Non-Goals

**Goals:**
- Add new filter types without redesigning routing/state each time.
- Support immediate local exploration over a bounded candidate set.
- Preserve authoritative whole-result filtering and reproducibility.
- Allow future score-producing models to declare score identity/version/scale.

**Non-Goals:**
- No arbitrary executable filter expressions.
- No requirement for a Bayesian model or any specific score algorithm.
- No complete-registry download to the browser.
- No plugin framework for third-party JavaScript.

## Decisions

### Use a discriminated typed filter model

Represent supported filter classes (Boolean, range, categorical, ontology and declared score-range) as typed data with backend validation. Keep field identifiers allow-listed; never evaluate user-provided code.

### Distinguish server filters from candidate-local filters

Every active filter has an execution scope. Server-capable filters can be serialized and applied to the full result set. Candidate-local filters operate only on the currently loaded bounded candidate set until explicitly promoted/refined server-side.

### Make candidate scope visible

If local filtering is not known to represent all matches, the UI must show the candidate-set size/scope and must not label local counts as whole-query counts.

### Derived score metadata is explicit

A backend-declared derived score should include stable field/key, human label, numeric bounds/interpretation where known, and model/definition version when applicable. This supports future posterior-probability or quality-score thresholds without assuming current semantics.

### Keep URL reproducibility for result-defining filters

Server-applied post-filters are serialized to the URL when compact. If future filter state becomes too large/complex, persist a validated saved-search/filter object server-side and put only its stable identifier in the URL.

## Risks / Trade-offs

- **Risk: users confuse candidate-only and full-set filtering** -> Visible scope indicators and separate authoritative refinement action.
- **Risk: generic filter model becomes an unsafe query language** -> Fixed filter types, allow-listed fields and server validation.
- **Risk: derived scores change meaning silently** -> Include model/definition version in returned metadata and saved state where relevant.
- **Risk: local state grows too complex for composables** -> Introduce Pinia only when concrete cross-branch state complexity warrants it and document the decision.
- **Risk: visualization components mutate search state inconsistently** -> Route all result-defining changes through the same typed filter/state API.

## Migration Plan

Start with one or two representative filter types and a candidate-scope indicator. Add server full-set equivalence tests before exposing a local filter as promotable/authoritative.
