# Workflow designer prototype

The local workspace is at `/workflows/design/`, linked from the separate, unchanged image-workflow gallery at `/workflows`. It uses the management cutover switch; disabling that switch returns the route to the legacy frontend. The interactive asset has an explicit unavailable state and a link back to the gallery.

Users select an EDAM data type and/or format, optionally restrict the operation and include related or unknown evidence, then add specific function snapshots. Each step retains its own inputs, outputs, resource and function references, schema revision and the vocabulary revisions used when it was selected. Steps can be duplicated, reordered, annotated and removed. Connections identify a specific output and input, allow branching, and prevent self-links, duplicate edges and cycles. The comparison distinguishes exact, related, unknown and conflicting data/format annotations, retaining the relationship direction and vocabulary revisions. Exact means only that recorded data and format identifiers match; all results require human interpretation and never assert that a workflow will run. A manual reason is required when the annotations do not establish an exact match. Reopened connection evidence is marked as stored until the user edits and rechecks it.

The draft is held in memory, with an unsaved-change warning and an explicit JSON download/restore path. Signed-in users may also save a private draft and deliberately share a read-only copy; see [drafts and sharing](workflow-drafts-and-sharing.md). Import checks version, size, shape, endpoint identity and graph cycles before replacing the existing draft. Imported snapshots require review against current public records, schema and selected vocabularies; changed functions remain available for inspection, while hidden or unavailable functions appear as placeholders, and neither is silently rebound. The designer rechecks both endpoints before adding or changing a connection. There is no executable export or execution.

The database-backed function endpoint `/_workflow/function/?ref=...` resolves a signed function reference, returns current public input/output annotations, and rejects unavailable, hidden or overlarge records. It is a live read rather than a transaction spanning an entire workflow; data can change after a check.

## Validation so far

The workflow graph unit tests cover branches, duplicates, missing endpoints, cycles, uncertain connections and tampered imports. Backend fixtures include multiple inputs and outputs, including an output with no format, and check their distinct identities. Desktop and mobile browser tests through both Apache and Caddy cover EDAM data/operation selection, duplicate steps, branching, graph display, connecting and editing, draft download/restore, changed snapshots, invalid imports, failed matching and missing assets. A separate keyboard journey selects a function, creates two steps, connects them and moves focus into connection editing. Backend tests cover both matching and function-detail visibility. The complete frontend unit suite and affected Django matching, EDAM, cutover and management tests pass.

The designer change is implemented and verified against these fixtures. Broader screen-reader and visual acceptance, representative production-sized matching performance and annotation coverage, and the sharing security review remain in the separate workflow-acceptance and production-readiness changes.
